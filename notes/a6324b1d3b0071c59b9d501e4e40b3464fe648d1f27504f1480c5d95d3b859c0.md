# Metaの広告ML特徴量基盤を高速化する「F3 Lightning」の仕組み

> [!abstract] AI要約
> Metaは広告ランキングモデル向けの特徴量基盤である[[Facebook Feature Framework]]（F3）を拡張し、新しいインフラストラクチャ層「F3 Lightning」を開発しました。従来のF3では、すべての特徴量を1つの巨大なグラフに統合して実行コストを削減していた一方、これが単一のリリース単位ともなっていました。そのため、1つの特徴量に不具合があると全体のリリースがブロックされる課題があり、取り扱う特徴量が2万件を超えるにつれて顕著になっていました。F3 Lightningはこの課題を解決するため、リリース境界と実行境界を分離し、各特徴量を独立してコンパイル、検証、デプロイ、ロールバックできるようにしました。独立したリリースを行いながらF3と同等の実行効率を維持するため、F3 Lightningでは4つの最適化が導入されています。第一に、内容に基づいて一意の識別子を付与することで、独立した設定間での重複計算を認識可能にしました。第二に、起動時にすべての特徴量をまとめて単一の実行計画とフラットな順序付きリストに変換し、共有処理を1回だけ実行します。第三に、リクエストごとに単一の共有メモリバッファを使用し、中間結果やリスト・マップの重複コピーを排除してキャッシュ効率を高めました。第四に、各識別子に密なインデックス割り当てを行い、リクエストパスでのハッシュ計算やポインタ追跡を不要にしました。これらの最適化により、インフラストラクチャの計算コストを増加させることなく、特徴量が本番環境に到達するまでの速度を従来のF3の約3.6倍に向上させ、より頻繁なモデルの反復と再学習を可能にしています。

![Figure 3: F3 Lightning separates the release boundary from the execution boundary.](<https://engineering.fb.com/wp-content/uploads/2026/10/Meta-F3-Lightning-Figure-3.png>)

## 重要ポイント

- F3 Lightningは特徴量のリリース境界と実行境界を分離し、各特徴量を独立してデプロイ・ロールバック可能にします。

![Figure 4: A bad feature no longer blocks a good one.](<https://engineering.fb.com/wp-content/uploads/2026/10/Meta-F3-Lightning-Figure-4.png>)
- 内容から一意の識別子を導出することで、独立した特徴量設定間で重複する計算を識別して排除します。

![Figure 6: The same computation gets the same identifier.](<https://engineering.fb.com/wp-content/uploads/2026/10/Meta-F3-Lightning-Figure-6.png>)
- 起動時に単一の実行計画を構築し、フラットなリストとして順序付けすることで実行効率を維持します。

![Figure 5: Features are selected from a priority queue by impact and risk.](<https://engineering.fb.com/wp-content/uploads/2026/10/Meta-F3-Lightning-Figure-5.png>)
- リクエストごとに単一の共有メモリバッファと密なインデックスマッピングを採用し、メモリアクセスを最適化してCPUコストを削減します。

![Figure 8: All features share one memory buffer.](<https://engineering.fb.com/wp-content/uploads/2026/10/Meta-F3-Lightning-Figure-8.png>)
